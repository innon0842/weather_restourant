# Engineering Notes

## 1. 설명 가능한 규칙 기반 추천

### 문제

초기 서비스에는 개인화 모델을 학습할 만큼 사용자 데이터가 없습니다.

### 선택

날씨, 시간대, 거리, 음식 키워드를 조합한 규칙 기반 점수를 적용했습니다.

### 결과와 트레이드오프

- 학습 데이터 없이 바로 추천할 수 있고 추천 이유를 노출할 수 있습니다.
- 반면 키워드에 없는 음식 특성은 반영하기 어렵습니다.
- 클릭·예약 데이터가 쌓이면 사용자 선호 가중치를 추가하는 방식으로 확장할 수 있습니다.

## 2. 외부 API 응답 정규화

### 문제

Kakao 장소 데이터와 공공데이터의 응답 구조는 화면에서 바로 쓰기 어렵고 변경 가능성이 있습니다.

### 선택

서버에서 카테고리, 날씨 태그, 좌표, 상세 정보를 애플리케이션 형식으로 변환했습니다. 클라이언트는 정규화된 응답만 사용합니다.

### 결과와 트레이드오프

- 외부 형식이 바뀌어도 파서와 서비스 계층을 중심으로 대응할 수 있습니다.
- 파서 일부는 외부 응답의 유연한 구조를 처리하기 위해 넓은 타입을 사용하고 있어 후속 타입 정리가 필요합니다.

## 3. 병렬 검색과 중복 제거

Kakao Local API의 검색 결과를 최대 3페이지까지 병렬로 요청한 뒤 장소 ID로 중복을 제거합니다. 넓은 검색 반경에서도 대기 시간을 줄이면서 최대 45개의 후보를 확보하기 위한 선택입니다.

## 4. 지연 상세 조회와 캐싱

목록 단계에서는 추천에 필요한 최소 정보만 사용합니다. 사용자가 식당을 선택했을 때 영업시간, 메뉴, 사진을 조회하고 PostgreSQL에 캐시합니다. 상세 API 실패 시에도 기본 식당 정보는 유지합니다.

## 5. 보안 경계

- 비밀번호는 bcrypt로 처리합니다.
- DTO 이외의 입력값은 전역 Validation Pipe에서 제거하거나 거부합니다.
- 예약과 사용자 API는 JWT Guard로 보호합니다.
- 서버용 API 키와 JWT Secret은 환경변수에서만 읽습니다.
- 업로드, 환경변수, 빌드 결과는 Git 추적 대상에서 제외합니다.

## 현재 한계

- `synchronize: true`는 개발 편의를 위한 설정이므로 운영 환경에서는 마이그레이션으로 전환해야 합니다.
- 프로필 이미지는 로컬 파일 시스템에 저장하므로 다중 인스턴스 배포 시 객체 스토리지가 필요합니다.
- 추천 규칙은 키워드 기반이라 메뉴 데이터가 부족한 식당을 정확히 분류하기 어렵습니다.
- 자동화 테스트는 기본 단위 테스트 중심이며 추천 점수와 예약 흐름의 통합 테스트 보강이 필요합니다.
- 클라이언트 린트는 오류 없이 통과하지만 기존 미사용 코드 관련 경고가 남아 있습니다.
